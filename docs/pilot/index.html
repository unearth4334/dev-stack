Problem and evidence

The repository currently contains research, an inventory and an illustrative task manifest. It has no workspace provisioning, task supervisor, deployed control surface or durable result collector. Existing Portainer management is useful infrastructure, but it does not establish coding-task state or isolation. A separate Git branch does not isolate processes, databases, ports or credentials.

The initial research baseline evaluates existing tools and their constraints. The broader platform roadmap remains background; this page is the authoritative scope and phase numbering for the pilot.

Goals, boundaries and assumptions

Required outcomes are reproducible task environments, both agent runtimes, private remote operation, structured progress and follow-up, verified cancellation, restart reconciliation, scoped credentials, retained results and a demonstrated restore. The milestone ends with live two-to-five-worker evidence and an operator runbook.

Confirmed inputs: dev-host has an Intel Ultra 7 265, 64 GiB RAM and RTX 5070 Ti. QNAP hosts control services in its local Portainer environment; dev-host is managed through Edge Agent Standard. Hardware is operator-reported, not independently inspected. OS, storage, QNAP headroom, authentication modes and private routing remain Phase 0 gates.

The initial trust class is operator-approved repositories with synthetic development data. This is not a hostile multi-tenant service. Ordinary workers get neither production credentials nor host management authority. If required repositories are untrusted or need privileged builds, choose an appropriate VM/microVM boundary before running them.

Deferred work: GPU/local inference, multi-user SSO, high availability, Kubernetes, a custom general-purpose UI, mandatory central secret-manager migration, public previews, S3 storage, automated Git integration/deployment and comprehensive transcript analytics. A protected existing secret store and narrow injection are sufficient for the pilot if its scope and rotation tests pass. These deferrals do not waive credential isolation, private results or recovery.

Planning and issue publication are authorized setup work. Each future live rollout must identify its exact target and follow the existing deployment workflow. A milestone or installed skill does not give a coding worker unrestricted deployment authority.

A workspace is the filesystem and execution boundary; a session is the provider conversation; an attempt is one bounded execution. Keep their identifiers and lifecycles separate. The task contract records project profile, resolved base commit, pinned runtime/image/skills, limits, grant references and result requirements. The existing manifest remains illustrative until Phase 2 validates a concrete schema; never interpret arbitrary manifest fields as shell commands.

Control persists intent before acknowledging or dispatching it. A local supervisor owns each attempt and confirms process-tree termination. An expired lease marks uncertainty; reconciliation must prove the old writer stopped before retrying. During a short controller outage, already authorized work runs only until its local deadline and spools bounded events. New tasks/grants wait. External side effects are observed before replay.

Task states distinguish queued, provisioning, running, awaiting input, verifying, ready for review, succeeded, failed, cancelled and lost. Platform-specific states may map to these concepts. Agent exit, test verification and human review are separate evidence. Follow-up can occur at a safe turn boundary; an unsupported interactive approval must produce a blocked/denied outcome and explicit resume procedure.

Keep active checkouts and test databases on dev-host local storage. QNAP retains control metadata and captured results. Use independent clones first, isolated homes, per-task sidecars and narrow mounts. Prevent worker access to sibling data, the host Docker socket, operator credentials and management networks. Reviewed skill releases are pinned read-only; repository code and hooks execute inside the task boundary.

Initial admission settings: two ordinary tasks at 4 GiB each, two CPU-equivalent quota each, and one heavy build at a time. The provisional 64 GiB budget reserves 16 GiB for host/existing services, 8 GiB for support/headroom and 40 GiB for aggregate tasks. Include sidecars and VM overhead; revise from measured available RAM and disk. Five 8 GiB tasks exhaust that task allowance. The GPU is outside ordinary profiles.

Platform selection and consequential trade-offs

Phase 1 selects concrete components before implementation. Coder Workspaces is the first environment-management candidate; test QNAP placement, dev-host provisioning and edition entitlement. Coder's native agent is optional and cannot replace the required CLIs by assumption. OpenHands Agent Canvas is the first agent-UI candidate, subject to adapter compatibility and mitigation of its documented shared-origin editor/backend-key risk. A fixed-template native runner plus a private index is the fallback, not a mandate to build a new framework.

Choose one lifecycle owner for each resource. Portainer may observe task containers but must not compete with their workspace controller. Its Standard Edge tunnel does not provide general-purpose SSH, preview or Terraform connectivity. Use structured agent interfaces; SSH/tmux are operator access, and mosh is optional human convenience. Experimental transports must be tested at pinned versions and contained behind the selected private interface.

Docker Sandboxes or another established VM runtime is a conditional isolation option when the host and workload warrant it. Vibe Kanban's company shutdown/community transition and Daytona's unmaintained public core make them reference designs rather than foundations for this pilot. Source evidence and qualifications are in the research report.

Phase 0 — Verify hosts, access, authentication, and pilot workload

Only reported hardware and intended placement are known. OS, QNAP capacity, credentials, private routing, and representative test workloads are not verified, so a deployable topology cannot yet be selected.

Scope

  • Complete a sanitized inventory of QNAP and dev-host, including OS/runtime, local disk, cgroups/virtualization, existing workloads and spare capacity.
  • Verify exact Portainer environments, TLS trust, edition and read-only diagnostics; establish a private control path independent of the Edge tunnel.
  • Confirm supported authentication for both Codex CLI and Claude Code, provider limits, operator access and authorized test targets.
  • Choose a trusted test repository, synthetic database fixture and deterministic checks; record allowed egress and live-deployment targets.

Non-goals: No live stack replacement, production credential distribution, GPU setup, or platform purchase.

Dependency: None; first phase.

Failure modes and implementation traps

  • The local terminal may not be dev-host; do not infer remote OS or runtime from local commands.
  • Do not publish private addresses, endpoint IDs, tokens, credentials, raw diagnostics or real project transcripts in this public repository.
  • A Portainer Edge connection is not a general SSH/API route. If OS or virtualization fails a candidate's requirements, record the alternative explicitly.

Observable completion criteria

  • Every required inventory field has observed evidence or an explicit blocking decision; the selected deployment path has no unresolved prerequisite.
  • Both CLI authentication paths succeed in an approved disposable environment without exposing credentials, and the selected fixture passes its baseline checks.
  • QNAP and dev-host can communicate over the intended private authenticated path, with management targets recorded privately and TLS verification enabled.
  • The inventory gives a measured RAM/disk admission budget and a named operator recovery path.

Verification: Read-only host and Portainer diagnostics; TLS/connectivity checks; minimal authenticated CLI smoke tests within the operator's grant; baseline fixture tests. Record commands, versions, sanitized results, and missing access as blockers.

Deliverables and documentation: Update docs/inventory.md and docs/decisions.md; add sanitized fixture requirements and an operator-owned private configuration template. Gate all implementation on the recorded environment and auth choices.

Rollback: Remove disposable authentication-test environments and revoke temporary credentials; do not change existing stacks.

Phase 1 — Select the pilot workspace owner and agent control surface

The research shortlist has consequential compatibility and licensing uncertainties. Building a custom scheduler or adopting multiple controllers before testing them risks duplicate ownership and rework.

Scope

  • Run a timeboxed vertical trial of Coder Workspaces and OpenHands Agent Canvas where Phase 0 prerequisites permit; compare against a fixed-template native runner.
  • Use one isolated disposable worker with a scoped credential for each required CLI. Exercise structured events, a follow-up turn, a denied action, cancellation and a retained patch.
  • Record exact versions, supported transports, auth behavior, service placement, resource ownership and paid-feature dependencies.
  • Select one workspace owner and one control path, with a narrow list of missing capabilities to implement. Evaluate microVMs only if the selected workload requires a stronger boundary or internal container builds.

Non-goals: No indefinite product search, new general-purpose agent framework, mandatory replacement of Codex/Claude by a native platform agent, or production rollout.

Dependency: Phase 0 must be merged and its gate passed.

Failure modes and implementation traps

  • Coder external-provisioner entitlement and remote Docker access must be verified; do not route Terraform through Portainer's Edge tunnel by assumption.
  • Canvas documents a shared-origin editor/backend-key risk; require a supported tested mitigation or reject that UI for the pilot.
  • Native CLI wrappers and experimental transports must pass the required lifecycle/auth tests at pinned versions. Two conversations in one backend are not two isolated workers.
  • No candidate may run trusted provisioning with repository-controlled mounts, hooks or templates outside the disposable task boundary.

Observable completion criteria

  • A committed decision records the winning composition, rejected alternatives, test evidence, license constraints and the sole owner of every resource.
  • Both required CLIs complete the trial through the selected control interface; denial, cancellation and follow-up behavior are observable without screen scraping.
  • The chosen topology supports private QNAP control and dev-host execution without unresolved credential or browser-origin blockers.
  • Downstream phase scopes name concrete components; each remaining gap has an explicit implementation owner and acceptance criterion.

Verification: Run the same fixture and control scenarios for each eligible candidate; capture sanitized events and measured startup/resource use. Timebox to two engineering days, recording any extension decision instead of silently expanding scope.

Deliverables and documentation: Commit the selection record under docs/pilot/ and update the plan plus downstream issues before Phase 2 begins. Retain only reusable trial assets, with pinned versions; remove abandoned candidate configuration.

Rollback: Remove trial services and credentials by exact ownership labels; restore the pre-trial resource inventory.

Phase 2 — Provision reproducible isolated workspaces with scoped credentials

The repository currently has no executable workspace lifecycle. Git branches alone do not isolate files, service data, runtime permissions or credentials.

Scope

  • Implement the Phase 1 workspace owner using platform-owned pinned templates and validated project profiles; independently clone an immutable base commit for each task.
  • Give each task its own branch, home, session state, network, dependency installation, database and volumes. Install a reviewed immutable shared-skills release.
  • Enforce aggregate task CPU/RAM/PID budgets, disk admission/quotas, narrow mounts, nonroot execution and tested management-network restrictions.
  • Deliver only project/model/artifact grants through an existing protected store or the selected secret manager. Keep bootstrap, Portainer release and host Docker authority outside workers.
  • Implement idempotent allocation, stop, retain and exact-resource destruction with a dirty-work safeguard.

Non-goals: No broad secrets-platform migration, shared writable worktree metadata, general NAS mounts, GPU allocation, or production deployment privilege.

Dependency: Phase 1 must be merged and its gate passed.

Failure modes and implementation traps

  • Readonly mounting a Docker socket does not make its API read-only; no host socket is allowed in a worker.
  • Task sidecars and VM overhead count against the budget. Bridge networks alone do not enforce all egress restrictions; test host/private addresses and IPv6.
  • Static keys remain usable after a secret-store token expires; document underlying credential rotation and refresh behavior.
  • Build hooks are untrusted execution. Run container builds in a separately constrained builder or supported task VM, not against the host daemon.

Observable completion criteria

  • Two workspaces can edit the same relative file, bind identical internal ports and migrate identical database names without shared state.
  • Worker probes cannot read sibling checkouts, operator auth, host sockets or unrelated secret paths, and cannot reach disallowed management services.
  • Observed runtime limits match the admitted aggregate budget; admission fails clearly under insufficient RAM/disk and unsupported requested privileges.
  • Creating the same allocation twice yields one owned workspace; destruction cannot target unrelated resources and preserves or explicitly exports dirty work.
  • Every workspace records base SHA, image/runtime/skills revisions and grant references without secret values.

Verification: Automated fixture lifecycle and negative boundary tests on the selected runtime; inspect effective limits and mounts; test credential scope/rotation and refusal of unsafe profiles. Store sanitized evidence for P01–P02, P07 and P11.

Deliverables and documentation: Workspace definitions, validated configuration contract, scoped credential/bootstrap runbook, skills lock/release reference, meaningful lifecycle tests and cleanup instructions. Update inventory and selected architecture.

Rollback: Stop new allocations, retain patches and named volumes, revert the pinned template, then remove only confirmed disposable resources. Revoke pilot grants when abandoning the deployment.

Phase 3 — Run both agents through a durable supervised task lifecycle

A running terminal is not a reliable task record. The pilot needs structured execution, follow-up handling, failure classification and confirmed cancellation for both required CLIs.

Scope

  • Implement or configure one adapter per required CLI behind the selected interface, preserving provider session IDs and pinned protocol versions.
  • Record tasks, attempts, workspaces, events, verification, grant references and pending input separately; persist intent before dispatch.
  • Support follow-up at a safe turn boundary and permission/denial handling. If an interface cannot answer interactive approvals, record a blocked result and a controlled resume path instead of auto-approving.
  • Add idempotency, attempt ownership, local deadline and bounded event spool, process-group cancellation and restart reconciliation.
  • Use platform lifecycle APIs where available; custom code is limited to gaps recorded in Phase 1.

Non-goals: No terminal screen scraping, autonomous privilege escalation, automatic deployment replay, new model harness, or unrestricted planner shell on QNAP.

Dependency: Phase 2 must be merged and its gate passed.

Failure modes and implementation traps

  • Session resume is provider/version dependent and distinct from restarting the same attempt. Never spawn a second writer merely because a heartbeat expired.
  • Exit code zero does not establish task success; test verification and agent outcome are separate.
  • A lost acknowledgement for an external side effect requires observation before retry. Cancelling a CLI must also stop child tests and servers.
  • Auth state and transcripts may contain secrets. Use isolated state and sanitized structured events; do not expose experimental listeners without a supported private boundary.

Observable completion criteria

  • Codex CLI and Claude Code each complete the fixture, accept a controlled follow-up, surface denied/waiting work and produce a provider session reference.
  • Duplicate submission/start and controller disconnect never produce simultaneous attempts writing the same workspace.
  • Cancellation is not reported complete until the task process tree is gone; a supervisor restart yields a recovered or explicitly lost attempt.
  • A failing test after a successful agent exit stays failed/ready for correction, never succeeded.
  • Event replay resumes after a sequence number without losing terminal state; local deadlines apply during a control outage.

Verification: Adapter contract tests and live smoke tests for both CLIs; inject disconnects, duplicate starts, denial, failed tests, child processes and supervisor restart. Capture P03–P08 and P14 evidence without publishing private transcripts.

Deliverables and documentation: Selected adapters/configuration, lifecycle/state documentation, failure-injection tests, auth compatibility matrix and operator resume/cancel runbook. Record unsupported semantics explicitly.

Rollback: Pause dispatch, reconcile and stop active attempts, preserve session/patch state, and revert adapter versions. Do not replay uncertain side effects.

Phase 4 — Deploy private QNAP control with recoverable dev-host execution

The pilot cannot yet be operated independently of a local terminal. It needs a durable QNAP entry point and authenticated control of dev-host without giving workers infrastructure authority.

Scope

  • Deploy the selected control service/UI and durable state on QNAP, with a trusted supervisor or supported provisioner on dev-host and a private authenticated connection.
  • Provide an operator task list showing runtime, task state, pending input, verification and links to task access/results. Reuse the selected UI; a simple authenticated index is sufficient if documented in Phase 1.
  • Expose submit, status, safe follow-up/resume, cancel and emergency stop for new dispatch; persist accepted requests before acknowledging them.
  • Configure least-privilege service accounts, TLS, restart behavior, bounded logs and a controller-state backup/restore procedure.
  • Deploy only the named pilot support stacks through the existing authorized Portainer workflow, with pinned artifacts and observed health verification.

Non-goals: No public agent API, multi-user SSO program, HA cluster, replacement of existing applications, or general-purpose custom dashboard.

Dependency: Phase 3 must be merged and its gate passed.

Failure modes and implementation traps

  • Pages hosts the public plan only; it must never host runtime credentials, private task results or the control API.
  • QNAP and dev-host may have different architectures; verify image manifests and avoid building on the NAS by accident.
  • Do not mount QNAP's Docker socket into an autonomous planner. Coder/Portainer/workspace ownership must remain unambiguous.
  • Schema upgrades must have a restore procedure. QNAP restarts must not trigger duplicate dispatch or erase waiting questions.

Observable completion criteria

  • An authenticated operator can submit one task of each runtime from the QNAP entry point and observe the true state without the initiating terminal remaining connected.
  • Unauthenticated callers cannot list or control tasks; worker identities cannot create privileged tasks or read the controller database.
  • Restarting the QNAP service preserves accepted work and pending input; running work reconciles once without duplicate writers.
  • The exact deployed artifact and health evidence are recorded, and a backup restores task state in a separate test location.
  • Existing nonpilot stacks remain healthy and unchanged by the rollout.

Verification: Private endpoint/auth negative tests, live two-runtime submission, controller restart during a bounded task, database restore and Portainer/application smoke checks. Record P03, P05 and relevant P12 evidence.

Deliverables and documentation: QNAP/dev-host deployment definitions, private configuration templates, access/control runbook, deployment/rollback evidence and public sanitized operating status. Update plan and phase issue.

Rollback: Pause admission, capture state, restore the previous pinned control artifact/database as required and preserve workers for reconciliation. Remove only named pilot support resources if reverting to manual operation.

Phase 5 — Publish durable results and validate safe retention and recovery

Task results must outlive their worker and be reviewable without exposing live workspaces or executable content to control-plane credentials.

Scope

  • Collect immutable per-attempt summaries, patches, verification and provenance, with optional plans/screenshots; validate upload paths, symlinks, size and content policy.
  • Publish a private authenticated results index on QNAP, linked from task status. Keep published output separate from live workspaces and public GitHub Pages.
  • Serve text/Markdown and downloads safely; render active HTML only on a verified isolated origin. Defer live application previews unless the fixture requires them.
  • Implement retention with separate stop/delete operations, dirty/unpushed-work safeguards, bounded logs/storage and artifact-backed cleanup.
  • Back up control state and results; test restore and worker loss, distinguishing recoverable captured output from lost uncheckpointed work.

Non-goals: No mandatory S3 service, public sharing, automatic Git merge/deploy, centralized raw transcript search, or production data fixtures.

Dependency: Phase 4 must be merged and its gate passed.

Failure modes and implementation traps

  • Artifact names are untrusted: reject path traversal, symlinks and archive escapes. A shared origin or parent-domain cookie can expose backend keys.
  • A partial upload must not look complete; publish the verified manifest last or atomically promote a completed directory.
  • Expiry does not authorize deleting dirty/unexported work. Retained databases and logs can exhaust disk too.
  • NAS snapshots alone may not be transactionally consistent for control databases; use the chosen database's supported backup method.

Observable completion criteria

  • A fresh authenticated browser can read the summary, download the patch and inspect verification after the source worker is destroyed.
  • Cross-task upload/read and path-escape probes fail; partial/oversized uploads are not listed as complete results.
  • Untrusted result content cannot execute with access to control-plane credentials; live workspaces and private artifacts are absent from the public Pages site.
  • Cleanup preserves unexported/dirty work, stops at configured limits and touches only owned resources.
  • A clean restore reconstructs task/result links and verifies artifact digests; any loss window is measured and documented.

Verification: Collector negative tests; destructive disposable-worker test; authenticated browser checks; disk-pressure and retention tests; control-plus-artifact restore. Record P09–P12 evidence.

Deliverables and documentation: Collector/publication configuration, result manifest contract, retention and backup/restore runbooks, recovery measurements and operator result links. Update task documentation.

Rollback: Disable publication/uploads, preserve completed manifests and backups, revert the collector version and keep workspace deletion disabled until capture integrity is revalidated.

Phase 6 — Validate two-to-five-worker operation and hand over the pilot

Individual feature checks do not prove concurrent operation or recoverability. The milestone needs an end-to-end acceptance record and an operator handoff on the actual hosts.

Scope

  • Run the representative workload with one Codex and one Claude worker, then a mixed five-worker load within the measured admission budget.
  • Exercise all required acceptance scenarios, including denial, cancellation, disconnect/restart, failed tests, credential expiry, retained results and restore.
  • Soak for one representative working day with repeatable tasks; observe queue state, RAM/disk, provider limits and orphan resources. Record longer-term monitoring as follow-up if needed.
  • Document startup, shutdown, resume, emergency stop, secret rotation, version update, backup/restore and safe cleanup for the operator.
  • Reconcile milestone issues, evidence and outstanding risks. Move genuinely deferred work only with an explicit reason; do not waive failed pilot gates.

Non-goals: No production deployment, GPU/local-model launch, multi-user onboarding, or automatic merge queue. No claim of production-grade availability from a one-day pilot.

Dependency: Phase 5 must be merged and its gate passed.

Failure modes and implementation traps

  • Five workers can contend on disk/builds or provider quotas despite available RAM. Report validated concurrency and bottlenecks honestly.
  • Hardware or license blockers require a recorded scope decision; a queued fifth task is not evidence of five simultaneous workers.
  • Do not run destructive drills on unrelated services or copy real secrets/transcripts into public evidence.

Observable completion criteria

  • Both runtimes operate concurrently from the QNAP entry point; a measured mixed five-worker run completes without boundary violations, missing accepted tasks or unaccounted resources.
  • Required acceptance scenarios P01–P14 pass with commands, versions and sanitized evidence; any failure keeps the milestone open.
  • A representative working-day soak has bounded disk/log use, no unexplained orphans and documented provider/capacity behavior.
  • The operator can recover a task and restore control/results using the committed runbook, with observed recovery time and loss window.
  • All prerequisite PRs are merged, plan/issue status matches deployed behavior and every deferred enhancement has an explicit follow-up record.

Verification: Run the complete pilot acceptance matrix on the actual QNAP/dev-host setup and record the tested commit/image/CLI versions, concurrency timeline, resource peaks, failures and restore evidence. Do not substitute mocks for live runtime acceptance.

Deliverables and documentation: Sanitized pilot acceptance report and operational runbook, actual private service links stored outside public Git, version baseline and follow-up backlog. Close the milestone only after the handoff gates pass.

Rollback: Return to the last validated concurrency and versions, pause dispatch if correctness is uncertain, retain artifacts/state and keep the milestone open until revalidation or an explicit scope decision.

Compatibility, release and rollback

No application-code or production-data migration is planned. Existing Portainer stacks stay under their current owner. New support services use exact names, pinned images and narrowly scoped credentials. Check QNAP/dev-host architecture and version compatibility in Phase 0; a container policy does not prove OS or VM compatibility.

Keep configuration templates free of secrets and private topology. Any task schema/state change needs a migration or an explicit disposable-state rule before rollout. Back up durable state using the database's supported method, preserve captured results, and test restore on a separate path. Do not assume reverting an image reverts database schema or external changes.

Each phase includes its own rollback. The operational sequence is pause dispatch, observe active attempts, preserve patches/state/results, restore known-good configuration and revalidate. Emergency stop limits new work; process cancellation still needs worker confirmation. Dirty-work deletion requires verified capture or an explicit operator discard decision.

The plan site is public and static, with no scripts, third-party assets, credentials or live control integration. Publishing it is separate from deploying private runtime services. Disable Pages or revert the page commit if documentation publication needs rollback.
